# Роль «Руководитель» для Наталии в БухКом — проект

## Итог (решено 25.11.2026, открытых вопросов нет)

Наталия — второе лицо в фирме после владельца (Стаса). Технически это новая роль «руководитель», а не второй
«владелец» в базе: роль владельца даёт полный доступ ко всем данным, а он ей не нужен.

| Что | Решение |
|---|---|
| Видеть клиентов | всех клиентов фирмы |
| Распределять клиентов | назначает и меняет «Ответственного бухгалтера» у любого клиента |
| Команда | приглашает и отключает бухгалтеров (не владельца) |
| Настройки фирмы | **может менять** (название, политика ПДн, ежемесячный отчёт) |
| Копии сообщений клиентов | на старте получает копии сообщений **всех** клиентов; это настройка — можно выключить для неё или отключить функцию полностью |
| Сообщения клиентов Наталии | всегда приходят и Стасу |
| Доступ к данным | только для контроля и распределения: карточки клиентов, переписка, статусы (сдача, задачи, «сдано»). **Нет** доступа к файлам чужих клиентов, Excel-отчётам по фирме, полной копии базы |
| Удаление клиентов и файлов | нет, только архив |
| Подписка | продлевает администратор сервиса; напоминания о сроке получает и руководитель |
| Контроль работы | экран «Работа команды»: что каждый сотрудник сделал и что за ним висит |

Код пока не менялся: доработку запускать отдельной командой.

## Часть 1. Простыми словами

### Какие роли есть сейчас

В программе всего **две роли** (`db.py:32`):

- **Владелец** (в коде `owner`). Это тот, кто зарегистрировал бухгалтерию. В интерфейсе он подписан словом
  **«руководитель»** (`web/app.js:336`, `web/app.js:874`). Отдельной роли «руководитель» нет: это просто подпись
  у владельца.
- **Бухгалтер** (`accountant`). Это все, кто пришёл по приглашению.

Стать владельцем можно только одним способом: зарегистрировать новую бухгалтерию (`api.py:157-166`,
`services.py:42-54`). Приглашение всегда создаёт бухгалтера (`botlogic.py:117-121`). Кнопки «сделать
руководителем» в программе нет.

### Хватит ли просто сделать Наталию вторым владельцем?

Технически это возможно уже сейчас, без доработки программы. Нужна одна команда на сервере, которая поменяет
роль Наталии в базе данных. Программа к двум владельцам готова: уведомления владельцам рассылаются всем по списку
(`scheduler.py:119`, `botlogic.py:127`).

Наталия получит:

| Требование | Если сделать её вторым владельцем |
|---|---|
| 1. Видит всех клиентов фирмы | ✅ Да (`control.py:11-12`) |
| 2. Назначает ответственного бухгалтера любому клиенту | ✅ Да (`api.py:282-291`, `web/app.js:706-712`) |
| 3. Сводка по работе каждого бухгалтера | ❌ Такого экрана нет. Видны только общие просрочки фирмы. |
| 4. Права «между бухгалтером и владельцем» | ⚠️ Нет. Она получит **все** права владельца: удалять клиентов и файлы, менять настройки и политику обработки данных, приглашать и отключать бухгалтеров, скачивать полную копию базы. Отключить Стаса она не сможет (`api.py:710`), но и Стас не сможет убрать у неё права без правки базы. |
| 5. Сообщения её клиентов приходят и Стасу | ❌ Нет. Уведомление получает только ответственный за клиента (`services.py:249-256`), даже если оба владельцы. Кроме того, клиент, которого Наталия создаст сама, автоматически закрепится за ней (`api.py:297`, `services.py:147`). |

**Вывод.** Второй владелец закрывает пункты 1 и 2 полностью, пункт 4 только с избытком прав, а пункты 3 и 5 не
закрывает. Это годится как временное решение «на сегодня». Для полноценной роли нужна доработка.

### Что предлагается

Появятся три роли:

- **Владелец (Стас)** — всё, как сейчас.
- **Руководитель (Наталия)** — новая роль. Видит всех клиентов, назначает ответственных, приглашает и отключает
  бухгалтеров, видит сводку по работе команды.
- **Бухгалтер** — как сейчас, только свои клиенты.

Права по ролям:

| Что | Бухгалтер | Руководитель (новое) | Владелец |
|---|---|---|---|
| Видеть клиентов | только своих | **всех** | всех |
| Назначать ответственного | нет | **да** | да |
| Добавлять, менять, отправлять клиента в архив | свои | **все** | все |
| Удалять клиента навсегда | нет | нет (только архив) | да |
| Удалять файлы | нет (сейчас есть дыра, см. ниже) | нет | да |
| Настройки (название, политика ПДн, ежемесячный отчёт) | смотреть | **менять** (решено 25.11.2026) | менять |
| Приглашать бухгалтеров | нет | **да** | да |
| Отключать бухгалтеров | нет | **да**, кроме владельца и руководителей | да, кроме владельца |
| Назначать или снимать руководителя | нет | нет | **да** |
| Подписка | видит срок | видит срок и получает напоминания | видит срок и получает напоминания |
| Excel по клиентам, счетам и контролю | по своим | **по всей фирме** | по всей фирме |
| Полная копия базы (ZIP со всеми файлами) | нет | нет | да |
| Сводка «Работа команды» | нет | **да** | да |
| Рассылка | своим клиентам | **всем** | всем |
| Панель администратора сервиса | только по номеру в настройках сервера | так же | так же |

Подписку продлевает **администратор сервиса** через свою панель (`api.py:810`), а не владелец фирмы. Сейчас
администратор — Стас (его Telegram-номер записан на сервере). Роль в фирме на это не влияет (`auth.py:76-81`).

Уведомления (пункт 5):

- Сообщение или файл от клиента получает ответственный бухгалтер **и всегда владелец**. Если ответственный
  и есть владелец, второе сообщение ему не придёт.
- Можно добавить отдельную галочку «получать копии по всем клиентам» для руководителя.

Сводка «Работа команды» (пункт 3) — новый экран «Ещё» → «Работа команды». По каждому сотруднику за выбранный
период будет видно:

- **За кем что числится сейчас:**
  - сколько у него клиентов;
  - просроченные отчёты;
  - просроченные задачи;
  - неоплаченные и просроченные счета;
  - сообщения клиентов без ответа;
  - клиенты, которые не подключились к боту.
- **Что он сделал за период:**
  - сколько ответил клиентам и как быстро;
  - сколько отметил отчётов «сдано» или «не требуется»;
  - сколько отправил файлов;
  - сколько напомнил об оплате.

После небольшой доработки базы данных в сводку добавятся созданные и закрытые задачи, выставленные и закрытые
счета (сейчас программа не запоминает, кто это сделал).

### Ошибку с удалением файлов исправим заодно

Сейчас кнопка удаления файла видна только владельцу (`web/app.js:560`), но сервер это не проверяет
(`api.py:518-524`). Бухгалтер, который разбирается в технике, может удалить файл своего клиента в обход
интерфейса. Нужно добавить проверку на сервере.

### Объём работы

Это три небольших пакета изменений, примерно 400–600 строк вместе с автотестами. Из них самая аккуратная часть —
изменение структуры базы. Перед ним нужно сделать резервную копию: ночная копия уже настроена.

1. Роль «руководитель», права, уведомления Стасу, исправление удаления файлов.
2. Запоминание, кто создал или закрыл задачу, счёт или файл, плюс журнал действий.
3. Экран «Работа команды».

### Что нужно решить вам

1. Можно ли руководителю менять настройки фирмы? В проекте — нет, потому что в настройках текст политики
   обработки данных, а за него юридически отвечает оператор.
   **Решено (25.11.2026, Стас):** да, руководитель **может** менять настройки фирмы
   (название, политика ПДн, ежемесячный отчёт). Проверка `api.py:728` должна пускать owner и manager.
2. Должна ли Наталия получать копии всех сообщений клиентов или только своих?
   **Решено (25.11.2026, Стас):** на старте руководитель получает копии сообщений **всех** клиентов фирмы.
   Это должно быть настраиваемым: позже включить или выключить копии для руководителя или отключить
   функцию полностью. Реализовать как настройку `users.notify_all` (по умолчанию 1 для руководителя),
   переключаемую в интерфейсе.
3. Нужно ли руководителю скачивать полную копию базы? В проекте — нет.
   **Решено (25.11.2026, Стас):** полный доступ ко всем данным фирмы руководителю **не нужен**.
   Ей доступно только то, что нужно для контроля и распределения клиентов: обзор всех клиентов,
   переписки с ними и статусы (сдача отчётности, задачи, «сдано»), назначение ответственного.
   Без доступа ко всем документам (файлам клиентов), Excel-отчётам по фирме, полной копии базы
   и прочим данным фирмы. При реализации это сужает права из раздела 2.3 B/D: видимость клиентов
   для руководителя расширяется только на карточку, чат и статусы, а не на всё, что проходит через
   общую проверку доступа к клиенту (`api.py:82-88`).

## Часть 2. Техническая часть

### 2.1. Текущая модель (факты)

- **Роли.** `users.role CHECK (role IN ('owner','accountant'))` (`db.py:32`). У пользователя есть флаг `active`
  (`db.py:36`), его проверяет `api.py:48`.
- **Кто становится владельцем.** Только через `services.create_agency` (`services.py:42-54`), который вызывается
  из `POST /api/register` (`api.py:157-166`). Приглашение всегда создаёт `accountant` (`botlogic.py:117-121`).
  API для смены роли нет: `staff_update` меняет только имя (`api.py:695-702`).
- **Проверки ролей:**
  - видимость клиентов (`control.py:9-13`);
  - доступ к клиенту (`api.py:82-88`);
  - назначение ответственного (`api.py:282-291`);
  - удаление клиента (`api.py:329-331`);
  - `owner_dep` (`api.py:69-72`): его используют `staff_invite` (685), `staff_update` (695), `staff_remove` (706),
    `settings_put` (728);
  - ZIP-копия (`api.py:751`, `api.py:925`).
- **Миграций нет.** `SCHEMA_VERSION = 1` (`db.py:9`) только записывается в `meta` (`db.py:203-206`), но нигде не
  сравнивается. Схема создаётся через `CREATE TABLE IF NOT EXISTS`.
- **Уведомления о клиенте.** `client_recipients`: ответственный, иначе владельцы (`services.py:249-256`). Её
  вызывает `notify_staff_about_client` (`services.py:263-266`) из шести мест в `botlogic.py` (208, 270, 286, 302,
  314, 319). Утренняя сводка строится по `visible_clients(user)` (`scheduler.py:32-33`). Напоминания о подписке
  получают только `owner` (`scheduler.py:119-124`).
- **UI.** `isOwner()` (`web/app.js:50`) используется:
  - метка ответственного в списке (397);
  - удаление файла (560);
  - удаление клиента (666);
  - выбор ответственного (706);
  - команда (809, 875, 879);
  - настройки (811).

  Подпись роли — `web/app.js:336`, `web/app.js:874`.

### 2.3. Изменения

#### A. Модель ролей и миграция

1. **Механизм миграций в `db.init_db`** (`db.py:198-207`): читать `meta.schema_version` и последовательно
   применять шаги. Поднять `SCHEMA_VERSION` до 2.
2. **Миграция v2:**
   - Пересоздать `users` с `CHECK (role IN ('owner','manager','accountant'))`. В SQLite CHECK через ALTER не
     меняется. Порядок: `PRAGMA foreign_keys=OFF`, `users_new`, копирование, `DROP`, `RENAME`,
     `PRAGMA foreign_key_check`, `foreign_keys=ON`, всё в одной транзакции.
   - Альтернатива без пересоздания таблицы: колонка `users.is_manager INTEGER DEFAULT 0` при `role='accountant'`.
     Это дешевле, но хуже читается. Рекомендую пересоздание.
   - `ALTER TABLE tasks ADD created_by INTEGER, ADD done_by INTEGER`.
   - `ALTER TABLE invoices ADD created_by INTEGER, ADD status_by INTEGER`.
   - `ALTER TABLE documents ADD user_id INTEGER` (для `kind='sent'`).
   - Новая таблица `activity_log(id, agency_id, user_id, client_id, action, object_type, object_id, details,
     created_at)` с индексом `(agency_id, user_id, created_at)`. Туда пишутся: отметка или снятие сдачи,
     создание или закрытие задачи и счёта, смена ответственного, архив, отправка файла, удаление файла.
   - Опционально `users.notify_all INTEGER DEFAULT 0` (копии уведомлений по всем клиентам).
3. **Сотрудников отключать мягко, а не удалять:** `UPDATE users SET active=0` вместо `DELETE` (`api.py:714`).
   Сессии удалять как сейчас. Тогда авторство в истории сохранится. Это не требует миграции: `active` уже есть
   (`db.py:36`). Нужно проверить, что `tg_id`/`max_id` UNIQUE (`db.py:34-35`) не помешают повторному приглашению
   того же человека. Варианты: обнулять `tg_id`/`max_id` при отключении или реактивировать старую запись в
   `start_staff_invite` (`botlogic.py:108-121`).
